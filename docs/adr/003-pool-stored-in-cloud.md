# ADR-003: 菜池存储在云端（多端同步）

**日期**：2026-08-23
**状态**：Accepted

## Context

「我会做的菜」菜池是用户的核心数据。存储方案有 3 个选项：

| 选项 | 同步 | 离线 | 隐私 |
|---|---|---|---|
| (A) 云数据库 | ✅ 自动多端 | ❌ 需联网 | ✅ 数据库规则可强制按 openid 隔离 |
| (B) 本地 storage | ❌ 单设备 | ✅ 完全离线 | ✅ 天然隔离 |
| (C) 云数据库 + 本地缓存 | ✅ 多端 + 离线可用 | ✅ | ✅ |

## Decision

**采用 (A) 云数据库**，集合 `user_custom_dishes`。

**不采用 (C) 的原因**：
- 缓存逻辑增加复杂度
- 多端冲突处理麻烦
- 菜池数据小（每用户 ~10 道菜 = 1KB），重新拉取成本低

**不采用 (B) 的原因**：
- 用户换手机/重装微信 = 数据全丢 → 违反「用心生活」承诺

## Consequences

**✅ 好的影响**
- 微信云数据库免费配额 2GB，**永远用不完**（1000 用户 × 1KB = 1MB）
- 换手机/重装无感
- 数据强一致（不会有「我这边加了那道菜，手机没看到」）
- 可以给未来「家庭共享」留接口（多 _openid 关联一个菜池）

**❌ 代价**
- 必须有网络才能用
- 云函数调用有延迟（< 500ms）
- 多了一层云函数故障风险（需要做好降级）

**降级方案**：
- `cloud.getFridge()` 失败 → 本地 `dishes-data.js` 兜底
- `customDish.get()` 失败 → 用本地 storage 临时缓存

## 不可逆性

**可逆**。但要改存储后端需要写数据迁移脚本（菜池小，迁移成本低）。
