# ADR-004: 随机 vs 加权推荐

**日期**：2026-08-23
**状态**：Accepted

## Context

核心选菜算法的选择：

| 选项 | 智能度 | 速度 | 复杂度 |
|---|---|---|---|
| (A) 纯随机 | 0 | < 1ms | 极简 |
| (B) 加权随机（基于历史 likes/dislikes）| 中 | < 10ms | 中等 |
| (C) AI 排序（DeepSeek 出3 道带排序）| 高 | 2-5s | 高 + API 成本 |

## Decision

**采用 (A) 纯随机**，加一个**启发式过滤**（优先选包含冰箱食材的菜名）。

**过滤逻辑**：
```
候选 = 菜池 - 最近 7 天已抽
matched = 候选中菜名包含冰箱食材的
if matched.length >= 3: 从 matched 随机
else: 从候选随机
```

## Consequences

**✅ 好的影响**
- **不动脑**：用户明确说「不想动脑」（JTBD #6）
- **快到极致**：< 100ms 响应
- **零外部依赖**：无网络、无 AI 调用、无算法计算
- **结果可解释**：每次都是「随机」，没有「AI 推荐错了」的信任问题

**❌ 代价**
- 不会主动避开用户不喜欢的（v1 有 likes/dislikes 评分，v2 砍了）
- 不会主动推新菜（鼓励用户换口味）
- **菜池抽空** 时体验差（菜池 < 7 道且全吃过 → 没菜可选）

**菜池抽空时的降级**：
- 弹 toast：「7 天内都吃过了，加点新菜」
- 不强制跳 onboarding（避免打扰）

## 不可逆性

**完全可逆**。算法逻辑在 `pages/home/home.js` 的 `onRandomPick()`，30 行代码，改起来便宜。

## 未来可能加

- 评分系统：每次记录后让用户标 👍/👎 → 加权随机
- 「今天心情」输入 → 影响候选

但**目前不加**，YAGNI 原则。
